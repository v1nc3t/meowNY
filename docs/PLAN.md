# meowNY: Build Plan (local-first)

Companion to `postgres-schema.txt` (schema v3, written for Postgres; it is ported to SQLite in phase 1). Work top to bottom. Each phase ends with a "Done when" check, so you know when to move on.

**Size tags:** S = a few hours, M = a few days, L = a week or more (rough, for one person working part-time).

## Product goals

- **Local-first.** A standalone desktop app. No server, no accounts, no internet needed. Data lives in an encrypted SQLite file on your own machine.
- **Open source and easy to install.** Download, run. No Docker, no database to host.
- **Secure by design.** No network attack surface. Encrypted at rest, locked app, signed releases.
- **Phone copy that syncs.** The phone (Android first) keeps a full offline copy and syncs with the desktop on the home network, started by a QR code. Away from home it works alone. No server of any kind.
- **CLI for AI agents.** Ships with the desktop app, client side only.
- **Documents with the numbers.** Receipts and invoices stored encrypted and linked to transactions; the phone gets the ones you choose.
- **Who owes whom.** Debts, and bills shared with other people, kept in your own ledger. The other people do not need the app, but one who has it can take a bill from a QR code.

## Order and why

1. **Foundations and security first**, because the encrypted database, key handling and the data model are painful to retrofit.
2. **Core budgeting loop next**: categories, transactions, budgets. This is the product.
3. **Recurring, then charts**: both build on the core.
4. **Backup and export before anything that spreads your data to other devices.**
5. **CLI, then phone sync, then documents, then debts and splitting.** Packaging and release is a gate before sharing the app with anyone else.

Phone sync (phase 8) can move ahead of the CLI (phase 7) if you mostly use the app on your phone.

## What carries over from the server-based design

Kept: the React UI (`ui/src`), Zod schemas, money and date logic, and the schema design (effective-dated budgets, `client_uuid` idempotency, history triggers, constraint tests). Replaced: Express, PostgreSQL, Better Auth and the `server/` package. The old accounts, GDPR-service, admin board and deployment phases are dropped. There is no operator and no one else's data to protect, so what remains of them is: export your data, delete all your data, and the encrypted backup.

## Decisions already made

- App shell: Tauri (small, Rust, native OS keychain access). React client reused.
- Storage: SQLite encrypted with SQLCipher. Schema stays in TypeScript migrations.
- Query layer: Kysely with a SQLite dialect (revisit if the Tauri bridge makes Drizzle simpler).
- One local profile. No user ids in the schema.
- Budgets are effective-dated; recurring items use categories; history via database triggers.
- Money is handled as strings/decimals (or integer minor units) in code, never floats.
- Request validation with Zod at every boundary (UI to core, CLI to core, sync).
- Mobile-first rule: every new screen from phase 4 on is built mobile-first, so the phone app (phase 8) can reuse it.
- Time: months, due dates and "this month" are computed in the user's timezone setting, never in UTC by accident.
- The CLI never opens the database file directly. It talks to the running app through a local command API, described by a schema it can print (`meowny schema`).
- Every new desktop feature ships its CLI commands in the same change. The phone app (phases 8 and 9) gets none.
- Program names: the desktop app is `meowny-desktop` (`src-tauri/`), the command line is `meowny` (`cli/`), so both can be on the PATH.
- Phone app: Tauri mobile (same `ui/` and Rust core), Android first, iOS later (phase 12). Sync is a direct connection on the home network, started by a QR code the desktop shows and the phone scans. No server, relay or remote reach; the phone works alone away from home. Details in phase 8.
- No telemetry. The only optional network traffic is update checks. The sync connection never leaves the home network.
- Dropped on 2026-10-16: the bank connection through an aggregator (a read key to the whole bank history and a network client in the app) and phone capture from payment notifications (fragile, little use). Nothing in the app talks to a bank or to a service that holds bank data. Phases 9 and 10 now hold documents, and debts and splitting.

## Open decisions (decide when you reach the phase)

| Decision | Needed by | Notes |
|---|---|---|
| License (AGPL, MIT or Apache-2.0) | Phase 0 | Affects how forks and hosted copies can be used |
| Query layer: Kysely or Drizzle on SQLite | Phase 0 | Pick after a small spike with SQLCipher in Tauri |
| Key handling: OS keychain only, or passphrase as well | Phase 2 | Passphrase protects better if the machine is shared |
| Chart library | Phase 5 | Any that works with the frontend |
| CLI transport (local socket or loopback HTTP) and token mechanism | Phase 7 | Tokens must be revocable and stored hashed. Decided: loopback HTTP and hashed, scoped, expiring tokens (see phase 7) |
| Phone app shape: PWA with WASM SQLite, or Tauri mobile / Capacitor | Phase 8 | Decided 2026-10-15: Tauri mobile, Android first. A PWA cannot reach a plain-http address on the home network, needs HTTPS for the camera, and its storage can be evicted |
| Which sync transports, in which order | Phase 8 | Decided 2026-10-15: one only, a direct connection on the home network started by a QR code. No Tailscale, WebRTC, shared folder or relay (no server, fewer dependencies) |

  - [x] a budget's type must match its category's type

  - [x] a category type cannot change after creation

**Done when:** a fresh database builds from migrations only and all constraint tests pass on SQLite.

## Phase 2: App security (M)

- [x] Database encrypted at rest. The key comes from the OS keychain, optionally combined with a passphrase. (`src-tauri/src/keys.rs`, `vault.rs`: random secret in the OS keychain; with a passphrase the key is HKDF(secret + Argon2id(passphrase)).)
- [x] Recovery key: shown once at setup and replaceable in Settings. It opens a separate wrapped copy of the database key, so "forgot my passphrase" and a lost keychain entry are both recoverable if it was saved. (`src-tauri/src/keys.rs`, `vault.rs`; the database key is random and stored only as two wrapped copies, one for everyday unlock and one for the recovery key.)
- [x] App lock: lock on idle timeout and on window close/minimize (configurable), optional biometrics where the OS offers it. Locked means the key is dropped from memory. (Idle timeout, minimize and close, configurable; connection closed on lock. Biometrics are not done: they need a platform plugin per OS and are left for later.)
- [x] Tauri hardening: strict CSP, no remote content, minimal allowed commands, no shell access from the webview, external links open in the system browser (Strict CSP, one permission per command, navigation guard, https links via the opener plugin.)
- [x] No network access unless a feature the user turned on needs it. A test or CI check lists every outbound call site. (`npm run check:outbound` in CI, allowlist in `scripts/outbound-allowlist.txt`. The old client code that still calls the server API is listed there and goes in phase 3.)
- [x] Safe logging: logs and crash reports never contain amounts, descriptions or keys (Fixed error codes only, panic hook prints the location only.)
- [x] "Delete all my data" action: wipes the database, keys and backups the app created, with confirmation (Needs typing DELETE. Also removes the keychain secret, which makes any leftover copy of the file unreadable.)
- [x] Settings: currency, locale, timezone (carried over from the old account page) (`ui/src/pages/SettingsPage.tsx`, route `/app/settings`. The old `AccountPage` is removed in phase 3.)
- [x] First-run screen: choose currency, set lock method, show where the data file lives (`ui/src/vault/`.)
- [x] Tests: wrong key cannot open the file, locked state holds no key, the database file contains no plaintext (Rust tests in `vault.rs`, `keys.rs`, `commands.rs`, `lib.rs`.)

**Done when:** the data file is unreadable without the key, the app locks itself, and you can wipe everything.

- [x] Replace `ui/src/http.ts` and the `fetch` calls with a typed command layer over Tauri (`invoke`), one place for validation and errors (`ui/src/api/`: answers are checked with Zod, failures are fixed codes. `http.ts`, the login/signup/account/landing/legal pages, `ProtectedRoute` and the `better-auth` client dependency are deleted; the app opens straight into `/app` behind the vault gate.)
- [x] Categories CRUD. Soft delete writes the NULL budget row (schema Part 5-A). (`src-tauri/src/categories.rs`; names trimmed, 1 to 50 characters, unique among active categories of a type; the NULL budget row uses the current month in the user's timezone.)

- [x] Budgets: set / remove a GLOBAL or CATEGORY budget from a given month, for both EXPENSE and INCOME (`src-tauri/src/budgets.rs`. Editing a month changes only that month: a month that already started keeps what it showed (the next month gets its own row if it would otherwise follow the change), while future months carry the newest value forward. The budgets page has a monthly history table (month, expense budget, spent, income budget, earned).
- [x] Budget overview: allocated vs unallocated, with a warning when categories exceed the global budget (Per side: budgeted, allocated, unallocated, actual, remaining and an over-allocated flag, computed from the effective budgets.)
- [x] Month filters and "current month" use the timezone setting, with a test around midnight at month end (`clock.rs` computes today and the month in the timezone setting; the transactions and budgets pages use it through the `today` command. Tests cover midnight at month end and year end.)
- [x] Tests: carry-over (a March budget applies in June until changed), removal via NULL, income budgets, idempotent create (`budgets.rs`, `transactions.rs`, `categories.rs`, `clock.rs`.)
- [x] Currency: pick from a list at first run; change it later in Settings with a typed exchange rate that converts every stored amount (transactions, planned amounts, recurring items, budget limits) in one transaction, rounded half up to the cent, or relabel only. No rate is fetched; the rate and date go to the history. (`src-tauri/src/currency.rs`, `ui/src/components/ChangeCurrencyModal.tsx`. Two decimals are still assumed for every currency, so JPY, KRW and similar show `.00`.)
- [x] Language and region: a language setting (separate from the number and date format and the timezone), chosen on the first-run screen together with format, timezone and currency, and changeable in Settings. All app text is translated (English, German, Spanish, French, Italian, Portuguese, Romanian) from one dictionary per language in `ui/src/i18n/`; text the person types is never translated. Adding a language is one new file plus a line in `languages.ts`; tests check every language has every key and the same placeholders. The recovery-key text file is still English, and amounts keep two decimals for every currency.
- [x] Speed and keyboard: SQLite runs in WAL mode with a larger cache; the transaction list reads straight from date-and-id indexes (newest 50 of 50,000 rows in under a millisecond in a debug build, from about 10 ms; deep pages and month filters about 15 to 50 times faster); the history table comes from two queries instead of one per month. In the UI every page loads on its own and starts loading on hover, number, date, currency and timezone formatters and option lists are built once, and search waits for a pause in typing. Keyboard shortcuts for navigation, adding, search, months and list rows, with hover hints and a `?` help dialog (`ui/src/keys/`, table in `shortcuts.ts`).

## Phase 4: Recurring items (M)

- [x] Recurring CRUD (income or expense, any category, interval unit + count, optional end date) (`src-tauri/src/recurring.rs`: create, update, delete, list. Exposed as the `*_recurring` commands and `ui/src/api/recurring.ts`. Changing the schedule moves the next due date to the first new occurrence on or after the old one. Deleting an item keeps its paid transactions. Later: the amount is optional. A bill that changes every time (electricity, a phone bill) has no fixed amount (`amount_minor` is NULL, migration `0006_recurring_amount_optional.sql`); each payment then says what was paid, and nothing is stored as planned. Such a bill is listed but left out of the monthly commitments, and the dashboard shows it as "varies". In the form, leave the amount empty; in an edit, clearing it makes the item varying. The migration rebuilds the table, so the runner now turns foreign keys off while a migration runs and checks them before it commits (a test shows the payments stay linked, and the migration was run on a copy of real data first).)
- [x] Due-date function computed from `start_date` (not from the previous due date). **Unit-test month-end cases** (Jan 31, Feb 29, yearly on Feb 29). (`recurring::due_date`, `next_after`, `first_on_or_after`; tests cover Jan 31, leap February and yearly Feb 29.)
- [x] "Mark as paid" in one database transaction (schema Part 5-B), with optional actual amount and payment date (`recurring::pay`. The planned amount is kept on the transaction. Paying the last occurrence before the end date makes the item inactive.)
- [x] Skip, pause, end; overdue and upcoming lists (`skip`, `set_active`, `end`, `dues`. Resuming an item past its end date is refused. Upcoming defaults to the next 30 days, at most 366.)
- [x] Due dates and "overdue" are evaluated in the timezone setting (`pay`, `end` and `dues` take today's date as an argument; the commands in the next batch pass the date from `clock::today`.)
- [x] Frontend: recurring list with due/overdue state and a mark-as-paid action, built mobile-first (`ui/src/pages/RecurringPage.tsx`, route `/app/recurring`, sidebar entry and `g r` shortcut. It reuses the transactions list layout, so it wraps on narrow screens. Status per row: overdue, due today, due on a date, paused or ended. Actions: mark as paid (amount and date prefilled), skip, pause or resume, edit, end, delete. All text is in the seven languages. Later restyled: a card for each item with the next date as an outlined badge (red when overdue, green when due today, dashed when paused or ended), "mark as paid", skip and pause right beside the date, and edit, end and delete underneath, quieter. A varying bill asks for the amount when it is marked as paid.)
- [x] Optional desktop notification for items due today (local only) (Once a day while the app is open and unlocked, one notification lists items due today or overdue; checked at start and every 30 minutes. A checkbox under Settings, notifications, turns it off; the choice is kept in the vault config file and is on by default. `ui/src/hooks/useDueNotifications.ts`, `show_due_notification` in `commands.rs`. Nothing is shown while the app is closed or for items that fall due later the same day.)
- [x] Tests: paying twice is rejected, planned vs actual amount stored, paid transaction counts in its category's actual (`recurring.rs` tests.)

## Phase 6: Backup and export (M)

- [x] **Encrypted backup**: one click writes a single encrypted file (passphrase chosen by the user), plus restore with a version check. Optional scheduled backups to a folder the user picks.
  - [x] Backup file and restore with a version check (`src-tauri/src/backup.rs`, commands `create_backup`, `restore_backup`, `restore_backup_new_vault`. The file holds every row as JSON, sealed with ChaCha20-Poly1305 under an Argon2id key from the backup passphrase (8 characters or more, not the app's), so it does not depend on the vault's keys and opens on a clean install. The header carries the schema version of the app that wrote it: a newer one is refused, an older one is loaded into a scratch database of that version and migrated forward. Restoring checks every constraint in the scratch database first and then replaces all data in one transaction, so a damaged file changes nothing. Over an open vault it needs the word RESTORE typed. `vault.json` (lock settings, notification choice) is not part of a backup. A test fails when a migration adds a table that the backup does not list.)
  - [x] Backup and restore screens (Settings, backup block: a passphrase typed twice and "back up now" opens a save dialog; restoring asks for the backup passphrase and the word RESTORE, then opens a file dialog and reloads the app. The first-run screen has "restore from a backup" (`ui/src/vault/RestoreFromBackup.tsx`), which sets an app passphrase for the new install and then shows its recovery key. Calls are `vault.createBackup`, `restoreBackup`, `restoreFromBackup`; new error code `invalid_backup` and new texts in all seven languages.)
  - [x] Scheduled backups to a folder the user picks (`src-tauri/src/schedule.rs`, migration `0005_backup_schedule.sql`, commands `get_backup_schedule`, `set_backup_schedule`, `clear_backup_schedule`. Settings, backup: a passphrase, daily, weekly or monthly, and a folder chosen in a dialog; the first backup is made at once so a folder that does not work is reported then. A timer checks every minute and backs up when due, only while the app is unlocked. A failed run is recorded, shown in Settings and tried again after an hour. Files are named `meowny-auto-<date>-<time>.meowbak`; the newest 10 are kept and only files with that exact name are deleted. The passphrase is stored in the encrypted database, in a table with no audit triggers; it is never sent to the UI and is left out of backups. Restoring does not change the schedule, and "delete all data" removes it but does not touch the backup files in the folder.)
- [x] **Export**: full JSON of all data, CSV of transactions. CSV safety: cells starting with `=`, `+`, `-` or `@` are prefixed with `'`. (`src-tauri/src/export.rs`, commands `export_json` and `export_csv`, client call in `ui/src/api/dataExport.ts`; the screen is the export screen item below. Both take a selection: a date range for transactions and a set of categories. With categories chosen, the JSON leaves out other categories, global budgets and the change history, and a test checks that no other category name leaks. The full JSON has settings, categories, every budget row, recurring items, transactions and the change history; amounts and ids are strings. The CSV has `date,type,category,name,amount,currency,description`, amounts positive, a byte order mark for Excel and CRLF line ends. Cells starting with `=`, `+`, `-`, `@`, tab or carriage return get a `'` in front (`export::neutralise`, shared with the Excel export). The files are written readable by the owner only. The scheduled-backup passphrase is never exported.)
- [x] **Excel export (.xlsx)**: one workbook with sheets for transactions, categories, budgets, recurring items and a monthly summary. Dates are real dates, money cells are numbers with the currency format (converted from the stored strings only at write time). The same formula-cell safety as CSV applies to text cells. (`src-tauri/src/export/xlsx.rs`, command `export_xlsx`, written with the `rust_xlsxwriter` crate; the tests take the file apart with a small reader of their own (plus `flate2`, a dev dependency, to unpack it). Sheets: Transactions, Categories, Budgets, Recurring, Monthly summary (income, expense, savings and savings rate for every month from the first to the last, quiet months as zeros). No cell holds a formula. Cells follow the person's number and date format setting: `ui/src/api/displayFormat.ts` reads the date order, the date separator and the symbol position from `Intl` and sends them as `DisplayFormat` (`src-tauri/src/display.rs`, shared with the PDF); the app turns them into Excel format codes with the separators and symbol as literals (`dd\.mm\.yyyy`, `#,##0.00" €"`). Digit grouping and the decimal mark are left to Excel, which takes them from the computer it runs on. The same selection as JSON and CSV limits every sheet. Dates before 1900 are written as text.)
- [x] **PDF reports**: a printable report for a chosen month or date range, with totals for income and expense, savings rate, budget vs actual per category, the charts from phase 5, and optionally the transaction list. Generated locally, with no network calls. Options: page size, include/hide descriptions (so a report can be shared without private details). (`src-tauri/src/report.rs`, `report/layout.rs`, `report/render.rs`, command `export_pdf`, written with the `krilla` crate, no network. The report covers whole months, from one month to another, optionally limited to some categories. Page 1: four tiles (income, expenses, savings, savings rate), income and expenses by month as bars, where the money went as a donut with a legend (top seven categories and the rest), then budget against actual per category as bars (over budget in red, categories without a budget marked), with the global budget on top. The transaction list is optional, repeats its headings on every page and shows descriptions only when asked. A4 or Letter, with page numbers. Numbers and dates follow the person's format (`DisplayFormat`, now also with decimal mark and group separator) and the fixed text comes from the app in the chosen language (`ui/src/api/reportLabels.ts`, 8 new texts in seven languages). The charts are drawn directly in the page, not copied from the screen. For a range, budget against actual compares each category over the months in which it had a budget; for one month it is exactly what the budget screen shows. Text is set in DejaVu Sans and Bold, embedded as subsets (`src-tauri/fonts/`, with its license): Latin, Greek and Cyrillic are drawn, a character outside them, such as Chinese, shows as `?`. The file has a title and no author or creation date. Limits: 120 months and 20,000 listed transactions.)
- [x] Export screen lets you pick the format (JSON, CSV, Excel, PDF), the date range and the categories, and shows what the file will contain before saving. A file with sensitive data is not encrypted unless you choose the encrypted backup, and the screen says so. (`ui/src/pages/ExportPage.tsx`, route `/app/export`, sidebar entry and `g e`; the choices are worked out in `exportPlan.ts` with tests. One format picker with a line about each; all dates or a from and to; all categories or a ticked list. For a PDF the dates widen to whole months and the screen says which, with a page size, a switch for the transaction list and a switch for descriptions (off by default). "What the file will contain" is a receipt on the right (it stays in view on a wide screen and comes last on a phone), filled from the new `export_preview` command: the number of transactions, the first and last date, the income and expense totals, and for JSON and Excel the categories, budget entries and recurring items, and for a full JSON the history. The format is four tiles, the categories are toggle chips grouped by expenses and income, and the export button shows the file extension. It follows the choice a moment after it changes and shows the same counts as the file; a choice that cannot be exported (end before start, no category ticked, a report over ten years) says why and disables the button. Dates, money and the language of the PDF come from the person's settings. The page ends with the plain warning that the file is not encrypted, with a link to the backup in Settings.) **Changed on 2026-10-16:** the period is chosen the same way for every format and the same way as on the transactions page: every date, or a range by day, month or year, with a "current month" button (`lib/range.ts` and `components/Pick.tsx` are shared by the two screens). Before, the date fields were always by day, and a PDF quietly widened them to whole months and then spoke in month names. A report is still made of whole months (its budgets, chart and comparison are monthly), so it offers month and year only, turns a range by day into the months it touches when chosen, and says why. The summary names the period in the unit that was chosen. The command line is unaffected (the exports already took exact dates, and a report takes months).

## Phase 7: CLI for AI agents (M)

The whole app is usable from the terminal, so scripts and AI agents can drive it without the UI. The CLI is a client of the running desktop app. No server is introduced. The CLI and the command API belong to the desktop app only: the phone app (phases 8 and 9) has neither.

Decisions made at the start of the phase (the open "CLI transport and token mechanism" row above):

- **Transport:** HTTP/1.1 on `127.0.0.1` only, on a random port that the app writes to `api.json` in its data folder. Plain `std::net`, no new crates. A plain `curl` works, which helps agents and the docs. Off by default; the switch lives in `vault.json` so the app can answer "locked" while the database is closed.
- **Browser safety:** every request carries `Authorization: Bearer <token>`, the `Host` header must be a loopback name, and a request with an `Origin` header is refused, so a web page cannot talk to the API.
- **Tokens:** `mny_` and 64 hex characters, kept as a SHA-256 in the encrypted database. A locked app cannot check any token, so it answers "locked" (exit code 3) to everyone. API calls do not count as activity: the idle lock still fires, and a script cannot keep the app open.
- **Routes:** one table in Rust lists every route with its scope (read, write, or needs the user at the app), arguments and summary. It is the single source of `meowny schema`, of the docs and of the test that fails when a route has no CLI command. The core is Rust, so serde validates the input; the schema comes from this table and not from Zod.

- [x] Design rule: the CLI is a thin client over the app's local command API, described by a schema generated from the Zod types. It never opens the database file. Validation, scoping and encryption stay in one place. Every feature through phase 6 gets a command; if the API lacks something, fix the API, not the CLI. (Done, with two differences from the first wording: the schema comes from the Rust route table, not from Zod types, and some features are left out on purpose because only the person at the app may do them: restoring a backup, changing the currency, the lock settings, tokens, setting up a scheduled backup and deleting everything.)

## Phase 8: Phone app (Android) and sync (L)

The phone keeps its own full copy of the data, works offline, and can change everything the desktop can change. Away from home it is used on its own; back home, the two sync. Both devices must be online at the same time on the same network, and every sync is started by a QR code that the desktop shows and the phone scans. **Android only for now** (an APK); the iOS app is in phase 12. The copy is small (about 10 MB for ten years of data), so storage is not a concern.

Decided with the maintainer on 2026-10-15:

- **No server of any kind.** No mailbox, relay, signalling or STUN service, no router port opening, no way in from outside the home network. So no WebRTC, no Tailscale address and no shared-folder transport. Away from home the phone simply works alone.
- **Very secure first, few dependencies second.** The sync uses only crates the app already has (`chacha20poly1305`, `hkdf`, `sha2`, `getrandom`, `zeroize`, and `argon2` for the phone passphrase) and `std` networking, like the command API. Only two new crates, both small and kept inside the sync code: a QR encoder (desktop) and a barcode scanner plugin (phone). If one of them breaks, pairing and sync stop and the rest of the app does not.
- **Tauri mobile**: the phone app is the same `ui/` and the same Rust core (`src-tauri/`) as the desktop, so all 7 languages and every screen come with it. Not a PWA: a web page cannot reach a plain-http address on the home network, cannot use the camera without HTTPS, and its storage can be evicted. The CLI and the command API stay desktop only.
- **Security rule for the phone:** a passphrase vault (no OS keychain crate on Android), auto-lock, and the phone erases itself after 5 wrong passphrases. The data comes back by pairing again with a QR from the desktop.

## Phase 9: Documents (M to L)

Keep the paper trail next to the numbers: the receipt of an online purchase, the invoice for the rent, a contract, a warranty. A document is a file stored encrypted on the device, linked to the transactions or recurring items it belongs to, and kept on the phone only when you choose. (This phase replaces the phone capture that was planned here: reading payment notifications is fragile and was judged not worth it.)

Decided with the maintainer on 2026-10-16:

- **A library with links.** A document exists on its own (a contract, a warranty) and can be linked to any number of transactions and recurring items (the rent invoice to each month's payment). Deleting a transaction never deletes a document, and a document with no links stays in the library.
- **Encrypted files next to the database, not blobs in it.** Each file is stored in a folder next to the database under a random name, sealed with ChaCha20-Poly1305 in chunks, with a key derived from the database key, so locking the app drops access to the files too. The database holds only the name, type, size, date, a hash of the contents and the links, so it stays small and fast after ten years of receipts.
- **To the phone only when chosen.** Every document has a "keep on phone" switch, off when it is added. The phone always has the list (name, date, links) and gets the file itself only when the switch is on. A document added on the phone is kept there until the desktop has it, and then dropped from the phone if the switch is off.
- **The phone can add documents too**: a photo of a paper receipt, or a file, attached to a transaction on the phone and synced to the desktop like any other change.
- **Every file is untrusted.** Nothing is run, and nothing is shown with scripts or remote content. Images are shown in the app after a size check. Every other type (PDF, HTML receipt, text) is opened by the system's own viewer from a private temporary folder that is emptied when the app locks or closes, with a warning that the copy is not encrypted while it is open. Saving a copy somewhere is an export and gets the usual warning. File names are cleaned (no folders, no control characters).
- **Limits.** 25 MB per file (a bigger one is refused with a message). The library shows its total size, and the phone shows how much it holds.

## Phase 10: Debts and expense splitting (L)

Keep track of money that is owed, in both directions, and of bills shared with other people. A friend is a name in your own ledger and does not need the app; a friend who has it can take a bill from a QR code. Nothing needs a server, and nothing leaves the device except a summary you save and send yourself or a code you show. (This phase replaces the bank connection that was planned here, which was dropped on 2026-10-16: a read key to the whole bank history and a network client are not worth the convenience.) The design is in `docs/debts-design.md`.

Decided with the maintainer on 2026-10-16:

- **Friends are names.** A friend has a name, and optionally a reminder. No accounts, no contact import, no phone number, email or address: nothing about a friend is stored but the name. There is no chat either (decided on 2026-10-16: a chat over the internet needs a server somebody runs, and people already have one); a bill code, and a summary you copy into the chat you already use, are the whole of the contact. Nothing leaves the device. A friend is archived, never deleted. A bill can also have a **guest**: a name typed for someone you do not track. Their part leaves your cost and makes no debt.
- **A ledger for each friend.** Entries are "I lent", "I borrowed", "they paid me back" and "I paid them back", each with a date, an amount in the app's currency, a note, and optional links to a transaction and to documents (a loan note, an invoice). The balance of a friend is the sum of the entries and of their parts of split bills: who owes whom, and how much. It is a running balance; a repayment is not matched to one bill.
- **Mark as paid** opens a dialog for the amount. An amount larger than the debt is accepted: the balance turns around and you now owe them the rest (the dialog says so before it is confirmed).
- **Repayments and loans are not transactions.** They live only in the ledger and never count as income or expense, so they cannot inflate your income or hide a real cost, and they never touch the budgets.
- **Splitting.** A bill you paid is split between you and some people, starting from an equal split, then by percent, by shares or by exact amounts. The amount of the transaction stays what was paid; the parts add up to it to the cent; **your part is never stored, it is the amount minus the others' parts.** A recurring item can carry a split template (kept as proportions), and every payment of it is then split by itself.
- **Budgets and statistics count only your part.** Pay 100 for a dinner shared by four, and the month shows 25, and so does the transaction list (with a mark that it was split). One definition of "what this transaction costs me" is used by every sum: the budgets, the dashboard, the trends, the PDF report, the exports, the API and the CLI.
- **Someone else paid.** The "I borrowed" form can add your part to your expenses at the same time. You owe them a debt; paying them back later is a ledger entry and never a second expense.
- **Bill codes (QR).** For each friend on a split bill the app can show a QR code of that friend's part (or the same text, to copy). A friend with the app scans it (phone) or pastes it (desktop), sees the details in a dialog, and accepts or denies. Accepting makes a debt in their ledger and, with a box ticked by default, an expense of their part; in another currency the dialog asks for a rate and shows the converted amount. No digits to type, no server, no inbox kept: a code is accepted on the spot or dropped. It is a notice and not a link: later edits do not follow, and the sender is not told.
- **Reminders.** A reminder is set per friend (a date, optionally repeating every N days) and rings while the balance is not 0. The time of day is a setting of each device. On the phone the system schedules it, so it rings with the app closed; on the desktop it rings while the app is open and unlocked, and what was missed is listed on the debts page. The text holds no name and no amount.
- **It follows the rest of the app.** Friends, entries and splits sync like everything else (stamps, deletion markers, written merge rules; a new protocol version), a currency change converts them with the same rate, and the backup, the exports, the CLI and "Delete all my data" include them.
- **A summary to send.** "Who owes what", or the statement of one friend, can be saved as text, CSV or PDF for you to send yourself; the app opens no connection to anyone.

## Risks to watch

| Risk | Mitigation |
|---|---|
| Laptop lost or stolen | Database encrypted at rest, app lock, key in the OS keychain, lost phones can be revoked from the desktop |
| Data lost with the machine | One-click encrypted backup, scheduled backups, restore test in phase 6 |
| Backup file leaks | Backups are encrypted with a user passphrase; unencrypted export is explicit and warned |
| Sync conflicts or lost edits | A stamp on every row from a hybrid clock, markers for deletions, merge rules written before code, a summary after each sync, convergence tests |
| Sync traffic exposed | Every message is sealed with keys that need both the pairing secret and the QR code shown at that moment; the network sees only ciphertext |
| Sync blocked on a network that isolates devices | Accepted: no server by design. The app says so and suggests the phone's hotspot; away from home the phone works alone |
| Phone lost or stolen | Passphrase vault, auto-lock, erase after 5 wrong tries, revoke from the desktop; no remote wipe without a server, so the passphrase must be long |
| A flaw in the sync protocol made here | Only standard parts (HKDF, ChaCha20-Poly1305), known-answer, tamper, replay and reflection tests, a review by someone else before release |
| CLI token leaked or over-privileged | Read-only default scope, expiry, hashed storage, destructive actions require the app |
| Malware on the machine reads unlocked data | Lock timeout, key dropped from memory on lock, minimal permissions; this cannot be fully removed |
| Malicious imported text | Escape on render, neutralise in CSV, treat every imported text and every document as untrusted |
| A document is malicious (a PDF, HTML or image from the internet) | Nothing is run or shown with scripts; only images are shown in the app, after a size check; everything else opens in the system's viewer; file names are cleaned |
| Documents leak through temporary copies | A private temporary folder, emptied when the app locks or closes; a warning that the open copy is not encrypted |
| Documents fill the phone | "Keep on phone" is off by default and per document, a size limit per file, and the phone shows what it holds |
| Wrong sums with split bills | One definition of what a transaction costs you for every query, a test that fails when a query uses the plain amount, random tests that the parts of a split add up |
| Tampered release or update | Signed installers and updates, checksums, SBOM |
| Money rounding bugs | Strings/decimals or integer minor units only, constraint tests, no float math |
| Scope creep | Finish and release phases 0 to 11 before starting phase 12 |
